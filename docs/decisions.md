# Принятые решения

Требования: [`docs/discovery/brief.txt`](discovery/brief.txt). Решения по открытым вопросам
приняты в порядке из skill `prior-art-first`: сначала требования и проверенные факты среды, затем
официальные рекомендации Microsoft, затем практика разработки Windows-приложений. Решения, которые
противоречат рекомендации Microsoft, приняты только потому, что этого требует бриф.

## 1. UI-платформа: WinUI 3 + Windows App SDK 2.5.1, .NET 9

**Почему.** Бриф требует «современное приложение для Windows на C#/.NET» и «нативные элементы
интерфейса», а спорные решения велел разрешать по рекомендациям Microsoft. Microsoft называет
WinUI 3 рекомендованным нативным UI-фреймворком для новых Windows-приложений:
[«WinUI 3 is the recommended native UI framework for building new Windows desktop applications»](https://learn.microsoft.com/en-us/windows/apps/winui/winui3/).
WPF при этом не устарел — [FAQ: «WPF is supported … It remains a good choice for existing WPF
apps and for new apps whose requirements fit WPF»](https://learn.microsoft.com/en-us/windows/apps/get-started/windows-developer-faq).
WinUI 3 выбран потому, что он даёт современные Fluent-контролы (`ListView`, `TreeView`,
`BreadcrumbBar`), которые ближе всего к прототипу, и при этом позволяет использовать нативные
Win32-элементы там, где это важно (TaskDialog, трей, Корзина Windows).

**Проверено в среде, а не по памяти:** минимальный WinUI 3-проект собран и запущен на этой машине
(.NET 9 SDK 9.0.308, Windows App SDK 2.5.1, `WindowsAppSDKSelfContained=true`, распаковка без
MSIX). Windows App SDK не требует установки рантайма на машине пользователя — он поставляется
вместе с приложением.

**Альтернатива.** WPF на .NET 10 остаётся разумным fallback, если понадобится Windows 10 в
условиях, где WinUI 3 недоступен. Отказ от WinUI 3 сейчас потребовал бы либо NuGet-доступа к
Windows App SDK (в этой среде сеть была ограничена), либо отдельной установки рантайма — оба
варианта хуже для воспроизводимой сборки.

**Ограничение.** WinUI 3 требует Windows 10 1809+; проверено на Windows 11 (сборка 26200).

**Стандартные контролы, а не копия прототипа.** Первая итерация интерфейса повторяла визуальный
стиль прототипа (кастомный заголовок, кастомные стили кнопок и полей). Заказчик явно потребовал
стандартное Windows-приложение: стандартные элементы, системная тема и аккуратный дефолтный вид,
а прототип использовать только как источник состава и расположения элементов. Интерфейс переделан
на дефолтные Fluent-контролы и стандартный заголовок окна (см. раздел 10).

## 2. .NET 9, с запланированным переходом на .NET 10 LTS

SDK 9.0.308 — единственный установленный; WinUI 3 и Windows App SDK 2.5.1 собираются и
запускаются на нём (проверено). .NET 9 — Standard Term Support, [поддержка до
10.11.2026](https://dotnet.microsoft.com/platform/support/policy/dotnet-core). Код не использует
API, специфичных для .NET 9, поэтому миграция — смена `TargetFramework` на
`net10.0-windows10.0.19041.0` после установки SDK 10 (LTS до 14.11.2028). Зафиксировано в README
как известное ограничение.

## 3. Состояние вкладок: JSON в `%LOCALAPPDATA%\PasteHatch\state.json`

Бриф оставлял формат открытым. Выбран один JSON-файл:

- `version` — версия схемы (текущая — 3);
- `activeUid` — активная корзина;
- `tabs[]` — порядок, UID папки, отображаемое имя и выбранная папка (`selectedFolder`);
- `window` — позиция/размер плавающего окна в физических пикселях.

Запись атомарная (`.tmp` + `File.Move(overwrite)`), чтение устойчиво к битому/отсутствующему файлу.
**Файлы на диске — источник истины:** папки в `Baskets` сканируются при старте, папки с валидным
UID, не попавшие в state, «усыновляются» (имя — по времени создания папки), а записи о
несуществующих папках отбрасываются. Поэтому потеря/порча `state.json` не теряет материалы.
Ограничение: если папок с валидным UID больше 10, восстанавливаются первые 10 — лишние папки
остаются на диске и не удаляются.

## 4. Рейка корзин: `ListView` слева, максимум 10, последняя не закрывается

**Требование заказчика.** Корзины должны быть вертикальной рейкой слева, а не верхними вкладками.
`TabView` вертикальную раскладку не умеет: у него нет ни свойства placement, ни vertical, и это
подтверждено перечнем API и открытым предложением
[microsoft/microsoft-ui-xaml#2194](https://github.com/microsoft/microsoft-ui-xaml/issues/2194).
`NavigationView` тоже не подходит: это навигация приложения, а не документные вкладки.

Реализовано:

- `ListView`-рейка слева: `+` в заголовке, строка корзины, кнопка `×` при более чем одной корзине,
  контекстное меню «Открыть в Проводнике / Переименовать / Закрыть корзину…»;
- закрытие проходит через подтверждение и Корзину Windows, последняя корзина не закрывается;
- двойной щелчок по строке включает переименование (`Enter` — сохранить, `Esc` — отменить);
- перетаскивание строк меняет порядок; клавиатурная альтернатива — `Ctrl+Shift+↑/↓`;
- `Ctrl+T`, `Ctrl+W`, `Ctrl+1…9` переключают корзины;
- порядок, названия и выбранная папка сохраняются в `state.json`.

## 5. Подтверждения: нативный TaskDialog, «Отмена» по умолчанию

- Бриф требует подтверждение перед отправкой в Корзину Windows.
- Microsoft UX guidance: подтверждение — модальный диалог, самый безопасный вариант должен быть
  кнопкой по умолчанию, разрушительное действие — нет
  ([Dialog Boxes](https://learn.microsoft.com/en-us/windows/win32/uxguide/win-dialog-box),
  [Confirmations](https://learn.microsoft.com/en-us/windows/win32/uxguide/mess-confirm)).
- Реализация — нативный Win32 TaskDialog (`System.Windows.Forms.TaskDialog`, который доступен в
  .NET через WinForms-профиль): кнопки «Отмена» (default) и «В Корзину Windows», иконка Warning;
  для корзины путь показывается в раскрывающемся блоке.

**Конфликт с рекомендацией Microsoft.** В [Confirmations](https://learn.microsoft.com/en-us/windows/win32/uxguide/mess-confirm)
фраза «moving a folder to the Recycle Bin» приведена как пример ненужного подтверждения, потому что
Корзина и есть undo. Приоритет отдан требованию брифа: подтверждение обязательно. Вместо
кастомного оверлея из прототипа используется нативный диалог (требование «нативные элементы»).

## 6. Трей: приложение живёт в области уведомлений

- Бриф: «при закрытии окна приложение остаётся в области уведомлений; правый щелчок по значку
  открывает меню с командой «Показать окно»».
- Реализация: WinForms `NotifyIcon` (обёртка над `Shell_NotifyIcon`). Левый щелчок по значку
  показывает/скрывает окно (привычное поведение утилит в трее); правый щелчок открывает меню
  **Показать окно** (bold, default), **Настройки**, разделитель, **Выход**; подсказка «PasteHatch».
- **Запуск.** Обычный запуск окно не показывает — приложение сразу живёт в трее; окно
  открывается щелчком по значку, командой «Показать окно», повторным запуском (single instance)
  или аргументом `--show`. Исключение — самый первый запуск (когда ещё нет `settings.json`): окно
  показывается один раз, чтобы пользователь нашёл приложение; это поведение отключается
  настройкой «Запускать в трее».
- **Окно действительно выходит на передний план.** WinUI 3 `Window.Activate()` не поднимает уже
  существующее окно, которое находится позади других, — это открытый дефект платформы
  ([microsoft/microsoft-ui-xaml#7595](https://github.com/microsoft/microsoft-ui-xaml/issues/7595)).
  Поэтому показ из трея после `Show()`/`Restore()` дополнительно вызывает Win32
  `SetForegroundWindow`; если Windows отказала в смене активного окна
  ([правила `SetForegroundWindow`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow)),
  окно всё равно поднимается в z-порядке без активации, чтобы пользователь его увидел. Тот же
  нативный вызов использует WinUIEx в обработчике левого щелчка по значку
  ([WindowManager.TrayIcon.cs](https://github.com/dotMorten/WinUIEx/blob/main/src/WinUIEx/WindowManager.TrayIcon.cs)).
- **Свёрнутое окно — не «видимое».** Win32 `IsWindowVisible` возвращает true и для свёрнутого
  окна, поэтому прежняя проверка «видимо → спрятать» по щелчку по значку прятала свёрнутое окно
  вместо восстановления. Теперь `IsIconic` отличает свёрнутое окно от видимого, и щелчок
  восстанавливает его на переднем плане.
- **Конфликт с рекомендацией Microsoft.** [Notification Area guidance](https://learn.microsoft.com/en-us/windows/win32/uxguide/winenv-notification)
  не рекомендует минимизацию в трей («Use the Minimize button … not the Close button») и советует
  меню «Open / Options / Exit». Требование брифа (жить в трее) приоритетнее; порядок меню и
  добавленная команда «Выход» следуют этой рекомендации.
- Один экземпляр приложения: именованный `Mutex` + событие; повторный запуск показывает окно
  работающего экземпляра и завершается. Это предотвращает два трей-значка и конфликт записи
  `state.json`.

## 7. Контекстное меню материала: нативный `MenuFlyout`

Microsoft: для элемента с основным назначением (текст/изображение) используется контекстное меню;
команды не должны быть доступны только из него; команда, требующая подтверждения, получает
многоточие; в меню не показывают сочетания клавиш
([Menus and context menus](https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/menus-and-context-menus),
[Command Menus](https://learn.microsoft.com/en-us/windows/win32/uxguide/cmd-menus)).

Реализовано: `Открыть`, `Открыть в Проводнике`, `Переименовать`, `Скопировать путь`,
`Вырезать`, `Копировать`, разделитель, `Удалить…` (многоточие — дальше подтверждение); меню
открывается правым щелчком, `Shift+F10` и клавишей меню; те же действия доступны с клавиатуры
(`Enter`, `F2`, `Delete`, `Ctrl+X/C/V`) и кнопками в строке — ничего не спрятано только в меню.

## 8. Буфер обмена и форматы материалов

Порядок разбора содержимого буфера: **FileDrop → Bitmap → UnicodeText** ([Standard clipboard
formats](https://learn.microsoft.com/en-us/windows/win32/dataxchg/standard-clipboard-formats)).
Чтение повторяется 10 раз по 40 мс при занятом буфере — официально документировано только то, что
«only one window can have the clipboard open at a time»; политика повторов — распространённая
практика, не документированная рекомендация.

Сохранение:

| Тип | Формат | Имя |
| --- | --- | --- |
| Скриншот/изображение из буфера | `.png` | `Пн, 13-02.png` |
| Текст из буфера | `.txt`, UTF-8 без BOM | `Пн, 13-02.txt` |
| Ссылка (однострочный http/https URL) | `.url` (Internet Shortcut, нативный формат Windows) | `Пн, 13-02.url` |
| Файлы из буфера/перетаскиванием | копия без изменения содержимого | исходное имя |
| Папки из буфера/перетаскиванием | рекурсивная копия, junction/symlink пропускаются | исходное имя или ` (2)` |
| Быстрая заметка | `.txt`, UTF-8 без BOM | `Пн, 13-02.txt` |

**Двоеточие и NTFS.** Бриф приводит имя заметки `Пн, 13:02.txt`, однако на Windows `:` в имени
файла запрещён: для NTFS это разделитель альтернативного потока данных (ADS), поэтому
`File.WriteAllText("Пн, 13:02.txt")` создаёт файл `Пн, 13` с потоком `02.txt`, а не ожидаемый файл
(дефект был найден юнит-тестами и исправлен). Поэтому имя корзины/отображаемое имя остаются
`Пн, 13:02` (как в брифе), а имя файла формируется функцией
`TabNameFormatter.FormatAsFileName` — все недопустимые для файловой системы символы заменяются
на `-`: `Пн, 13-02.txt`. Это зафиксировано тестами.

Коллизии имён разрешаются суффиксом ` (2)`, ` (3)` — соглашение Проводника Windows. Расширение
при переименовании не меняется; недопустимые символы, служебные имена (`CON`, `NUL`, `COM1`…),
точка/пробел в конце и превышение длины отклоняются с нативным сообщением об ошибке.

## 9. Именование корзин и UID

- Имя по умолчанию — сокращённый день недели и время: `Пн, 13:02` (пример из брифа). Культура
  зафиксирована `ru-RU`, потому что интерфейс русский и имя не должно зависеть от языка ОС.
- UID папки — 6 символов из алфавита без похожих `I/O/0/1` (как в прототипе), уникален среди
  папок и открытых вкладок.
- **Отображаемое имя корзины** хранится в `state.json` и не является именем папки — переименование
  корзины не ломает путь, который пользователь передал агенту.

## 10. Визуальный язык: стандартные WinUI-контролы и системная тема

**Почему.** Пользователь попросил «выглядеть как дефолтное Windows-приложение, красивое и
аккуратное», а прототип оставить только как источник состава экрана. Это совпадает с официальными
принципами Windows 11 — [«Calm: Windows 11 is softer and decluttered» и «Familiar: … There is no
learning curve»](https://learn.microsoft.com/en-us/windows/apps/design/design-principles) — и с
руководством по настройкам: «Keep settings pages simple and make use of binary (on/off) controls.
A toggle switch is usually the best control for a binary setting», «Define smart defaults and keep
the number of settings to a minimum», «When a user changes a setting, the app should immediately
reflect the change» ([Guidelines for app settings](https://learn.microsoft.com/en-us/windows/apps/design/app-settings/guidelines-for-app-settings)).

Что из этого следует и реализовано:

- **Стандартный заголовок окна** с системными кнопками «свернуть/развернуть/закрыть»; кастомные
  заголовок и caption-кнопки удалены (заодно ушла проблема «лишней» кнопки maximize).
- **Только дефолтные контролы и стили Fluent**: `ListView`-рейка для корзин, `CommandBar` для
  команд, `TreeView` для файлов, `BreadcrumbBar` для пути, `TextBox` + `Button` для быстрой
  заметки, `InfoBar` для ошибок, `MenuFlyout` для контекстных меню, `ToggleSwitch` в настройках.
  Кастомный словарь стилей из `App.xaml` удалён.
- **Системная тема**: приложение следует светлой/тёмной теме Windows; для тёмной темы title bar
  синхронизируется через `DWMWA_USE_IMMERSIVE_DARK_MODE` (WinUI 3 не всегда применяет его для
  unpackaged-приложений).
- **Структура экрана**: панель команд → три колонки (рейка корзин, дерево файлов, предпросмотр) →
  быстрая заметка → InfoBar ошибок → строка состояния с путём и числом элементов. Это три
  стандартные панели, как в проводнике и редакторах кода, а не копия прототипа.
- **Настройки — отдельное окно** с тремя булевыми настройками (запуск в трее, запоминание
  положения окна, поверх других окон), сразу применяются без OK/Cancel; точка входа — `…` на
  панели команд и пункт в меню трея, как рекомендует руководство по настройкам.
- **Компактность**: окно по умолчанию 1200×800 DIP, при этом свободно растягивается; ширина
  рейки и предпросмотра регулируется перетаскиванием. Первый запуск открывает окно, дальше
  приложение живёт в трее.
- **Создание корзины — кнопкой `+` в заголовке рейки.** Отдельная команда «Новая корзина» на
  панели команд не нужна: она дублирует рейку.

## 11. Остальные решения

- **Первый запуск** создаёт одну пустую корзину и один раз показывает окно; дальше приложение
  стартует в трее (см. раздел 6).
- **Папки в drag&drop/буфере принимаются**: копируются рекурсивно, как в Проводнике; junction и
  symlink не разворачиваются, чтобы копирование не зациклилось. Совпадения имён получают ` (2)`.
- **Ленивое live-наблюдение**: пока окно видимо, `FolderWatcher` слушает активную корзину через
  `FileSystemWatcher`; без опроса диска, с debounce и отключением при скрытии в трей. `F5` и показ
  окна остаются резервными способами обновления.
- **Иконка приложения** генерируется скриптом `scripts/generate-icon.ps1` (многоразмерный `.ico`,
  32-битные DIB-записи для совместимости с Win32/WinUI), бинарник не редактируется вручную.
- **Настройки** хранятся отдельно от состояния корзин — в `settings.json`, чтобы повреждённый
  файл настроек не влиял на корзины. Те же три значения имеют разумные дефолты и сбрасываются
  командой «Сбросить настройки» в окне настроек.
- **Тестовые швы** (в обычной работе не задаются): `PASTEHATCH_DATA_ROOT` изолирует папку данных,
  `PASTEHATCH_TEST_OFFSCREEN=1` показывает окно за пределами экрана без активации,
  `PASTEHATCH_TEST_NO_TRAY=1` не создаёт значок в трее. Всё это нужно, чтобы автоматические
  проверки не появлялись на рабочем столе пользователя. По умолчанию путь всегда
  `%LOCALAPPDATA%\PasteHatch` через
  [`Environment.SpecialFolder.LocalApplicationData`](https://learn.microsoft.com/dotnet/api/system.environment.specialfolder),
  как требует бриф.

## 12. Тестирование: юнит-тесты ядра + базовый smoke

- **Домен покрыт юнит-тестами** (`tests/PasteHatch.Core.Tests`, xUnit, 301 тест): именование,
  классификация, состояние, восстановление, коллизии, подтверждения, лимит корзин, ADS-регрессия,
  превью, дерево файлов, сортировка и операции с папками.
  Это дешёвые и стабильные проверки, которые стоит держать зелёными.
- **UI проверяется единым прогоном** (`scripts/verify.ps1`): заметка, корзины, единственный экземпляр, дерево, live-обновление, текстовый предпросмотр, копирование пути, вставка текста и вложенных папок, создание папки. Готовность окна и контролов — общая предпосылка сценариев. Доказательства сохраняются после очистки в `.scratch/verify-pastehatch/<GUID>/`.
- Сложный UI-сценарий на 20 шагов (диалоги, клавиатурные комбинации, drag & drop, изолированный
  рабочий стол) остаётся вне репозитория: он хрупкий и дорогой в поддержке. Спорные места
  проверяются одноразовыми ручными прогонами.
- **Изоляция**: проверка отказывается запускаться при открытом PasteHatch, использует отдельные данные и завершает только свои процессы. Буфер обмена сохраняется и восстанавливается; во время прогона не следует копировать другие материалы.

## 13. Дерево файлов: без анимаций появления

**Дефект.** При переключении корзин дерево на секунду становилось пустым, хотя данные уже были
готовы. Измерено на машине разработки: UI Automation отдаёт строки новой корзины через 2–8 мс после
выбора, а кадры экрана (запись области дерева, ~100 мс на кадр) показывают пустое дерево
примерно с 120 мс до 1000 мс после переключения — новые строки проявлялись только к 1–1.2 с.

**Причина.** Стандартный шаблон `ListView`/`TreeView` задаёт `ItemContainerTransitions` —
переходные анимации добавления, удаления и перестановки элементов. Перестройка строк старой
корзины и вставка новых запускали анимацию на каждый переход.

**Решение.** Для `FileTree` в `MainWindow.xaml` задан пустой `ItemContainerTransitions` —
содержимое показывается в том же кадре. Проверено повторной записью кадров: после правки первый же
снятый кадр содержит строки новой корзины, пустого кадра и секундной задержки нет.

## 14. Предпросмотр в панели, без отдельного окна

**Требование заказчика.** Файл с именем по времени (`Пн, 13-02.txt`) нужно узнавать, не открывая;
предпросмотр должен быть внутри окна, а не в отдельном окне.

**Решение.** Справа появилась панель предпросмотра (list/details). Для `.txt`, `.md` и `.url`
показывается начало файла в read-only `TextBox` (текст можно выделять и копировать), для
изображений — уменьшенная картинка, для остальных — тип, размер, дата, путь и кнопки «Открыть» /
«Скопировать путь». Markdown и HTML показываются исходником, PDF и архивы встроенно не
рендерятся: для них есть внешнее открытие. `MaterialPreview.ReadText` читает ограниченный
фрагмент (64 КБ), чтобы большой файл не подвешивал UI; старая двухстрочная подпись в строке списка
удалена, потому что дублировала панель и делала строки высокими.

**Почему не preview handlers/WebView2.** Нативные preview handlers требуют COM-хоста и дают
непредсказуемый набор форматов; WebView2 — тяжёлая зависимость и дополнительная поверхность
атаки. Для базового сценария «прочитать текст/увидеть картинку» достаточно стандартных контролов.

## 15. Копирование пути

**Требование заказчика.** Путь к папке и к конкретному файлу передаётся агенту; на панели команд
нужна кнопка «Скопировать путь», а для выбранного элемента — такая же команда в контекстном меню
и в предпросмотре.

**Решения и почему.**

- **Путь текущей папки — на панели команд.** Кнопка «Скопировать путь» видна всегда и копирует
  `SelectedFolderPath`, то есть папку, в которой находится выбранный элемент. Это тот путь, который
  чаще всего передают агенту.
- **Путь элемента — в предпросмотре и контекстном меню.** В панели предпросмотра есть кнопка
  «Скопировать путь»; в контекстном меню узла дерева — пункт «Скопировать путь». Так команда
  доступна мышью, тачем и клавиатурой без отдельной кнопки в каждой строке.
- **Путь без кавычек.** Строка копируется простым текстом: её получатель — локальный агент, а не
  командная строка. Формат единый для папки и файла.
- **Доступность.** У кнопок заданы `AutomationProperties.Name` и tooltip; элемент дерева имеет
  accessible name из имени файла.
- **Буфер — тот же сервис.** `BasketWorkspace.CopyEntryPath` вызывает `IShellService.CopyText`
  (повторы при занятом буфере уже реализованы в `ShellService`), ставит статус в строку состояния и
  сообщает об ошибке так же, как копирование пути папки.

**Проверено.** Юнит-тесты: копируется путь именно выбранного элемента, ошибка буфера показывается
пользователю, изменение приходит одним событием `Changed`. Headless UIA-прогон: кнопка
«Скопировать путь» в предпросмотре кладёт в буфер полный путь выбранного файла; кнопка на панели
команд копирует папку.

## 16. Переименование файлов и папок

**Требование заказчика.** Переименование — кнопкой в строке и `F2`, при этом у файла
редактируется только имя, а расширение видно рядом и не меняется. Папки переименовываются так же.

**Почему так.**

- **Явная кнопка — основная точка входа.** [Mouse and pointers](https://learn.microsoft.com/en-us/windows/win32/uxguide/inter-mouse):
  двойной щелчок выполняет default command, «advanced interactions must have consistent,
  predictable behavior», а «Don't make double-clicking and dragging the only way to perform an
  action». Поэтому переименование доступно кнопкой в строке, `F2` и пунктом контекстного меню.
  Двойной щелчок по названию больше не переименовывает: он, как и по остальной строке, открывает
  файл или папку. Это исправление прежнего нестандартного поведения (см. §18).
- **Расширение видно и не редактируется.** Инлайн-редактор содержит только базовое имя;
  расширение — отдельная подпись рядом, коммит сохраняет расширение. У папки расширения нет.
- **Клавиатурная альтернатива.** [Keyboard accessibility](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/keyboard-accessibility)
  требует, чтобы действия были доступны с клавиатуры; `F2`, `Delete`, `Enter` и контекстное меню
  работают и для файлов, и для папок.
- **Внешний drag&drop не сломан.** ListView с `AllowDrop` получает и внешние файлы, и внутренний
  drag с перемещением на папку; обработчики `DragOver`/`Drop` различают эти случаи.

**Проверено.** 301 юнит-тест, включая переименование файлов и папок, сохранение расширения,
коллизии, перемещение и копирование. Headless UIA-прогон: кнопка переименования открывает редактор
с именем без расширения, сохранение переименовывает файл на диске и оставляет расширение.

## 17. Перестановка корзин в рейке

**Требование заказчика.** Корзины можно переставлять друг относительно друга перетаскиванием;
порядок сохраняется.

**Почему так.**

- **Встроенный reorder `ListView`.** Для рейки нужны `CanReorderItems` и `AllowDrop`, а
  `CanDragItems` — чтобы приходили события ([ListViewBase.CanReorderItems](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/api/winrt/microsoft.ui.xaml.controls.listviewbase.canreorderitems)).
  Отдельно требуется [ReorderMode](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/api/winrt/microsoft.ui.xaml.controls.listviewbase.reordermode):
  значение по умолчанию `Disabled`, включён `Enabled`.
- **Синхронизация порядка.** Встроенный reorder меняет `_basketRows`, а не модель workspace.
  После `DragItemsCompleted` порядок UID передаётся в `ReorderTabs`; во время drag выбор корзины
  не активируется (`_isBasketDrag`), иначе перестройка рейки отменила бы перетаскивание.
- **Хранение.** Порядок уже является частью `state.json` (`tabs[]`), поэтому схема не менялась:
  `ReorderTabs`/`MoveTab` переставляют `_tabs` и сохраняют состояние. Неизвестные UID
  игнорируются, отсутствующие корзины добавляются в конец — устаревший drag не может потерять
  открытую корзину.
- **Клавиатурная альтернатива.** [Keyboard accessibility](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/keyboard-accessibility)
  и [Mouse and pointers](https://learn.microsoft.com/en-us/windows/win32/uxguide/inter-mouse)
  («Don't make double-clicking and dragging the only way to perform an action») требуют не
  оставлять перестановку только мышью. Добавлены `Ctrl+Shift+↑`/`Ctrl+Shift+↓`; во время
  переименования корзины сочетание остаётся текстовому полю.

**Проверено.** Юнит-тесты: порядок переживает перезапуск, неизвестные и пропавшие UID, `MoveTab`,
активная корзина не меняется, границы списка. Перестановка в UI проверяется вручную; отдельный
интеграционный drag-сценарий не держим — он хрупкий.

## 18. Три колонки: рейка корзин, дерево файлов, предпросмотр

**Требование заказчика.** Корзины должны быть слева, в центре — дерево файлов, справа — предпросмотр.
Файлы и папки вставляются через буфер и перетаскивание; путь копируется; дерево должно обновляться
при внешних изменениях, но без постоянного опроса диска.

**Какие источники прочитаны.**

- [Tree view](https://learn.microsoft.com/en-us/windows/apps/design/controls/tree-view): TreeView
  подходит для файлового браузера, но «The TreeView control is not virtualized», поэтому дочерние
  узлы заполняются при раскрытии (`HasUnrealizedChildren`), а не читаются целиком заранее.
- [BreadcrumbBar](https://learn.microsoft.com/en-us/windows/apps/design/controls/breadcrumbbar):
  компонент предназначен для навигации по папкам; путь к текущей папке всегда виден.
- [FileSystemWatcher](https://learn.microsoft.com/en-us/dotnet/api/system.io.filesystemwatcher):
  подписка на уведомления ОС, без опроса; несколько событий на одну операцию, поэтому нужен debounce.
- [InternalBufferSize](https://learn.microsoft.com/en-us/dotnet/api/system.io.filesystemwatcher.internalbuffersize):
  буфер по умолчанию 8 КБ, максимум 64 КБ, non-paged; при переполнении нужен повторный обход.
- [NotifyFilters](https://learn.microsoft.com/en-us/dotnet/api/system.io.notifyfilters): `LastAccess`
  срабатывает при открытии файла, поэтому его нельзя слушать — предпросмотр вызывал бы сам себя.
- [ReadDirectoryChangesW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-readdirectorychangesw):
  при переполнении буфера изменения нужно вычислять повторным перечислением.
- [Keyboard shortcuts in Windows](https://support.microsoft.com/en-us/accessibility/windows/keyboard-shortcuts-in-windows):
  `Alt+↑` — на уровень выше.
- [InfoBar](https://learn.microsoft.com/en-us/windows/apps/design/controls/infobar): InfoBar нельзя
  использовать для подтверждения действия, которое не меняет состояние приложения. Поэтому
  «путь скопирован», «добавлено» и другие краткие результаты ушли в строку состояния; InfoBar
  остался для ошибок и не закрывается сам через 6 секунд.
- [Status bars](https://learn.microsoft.com/en-us/windows/win32/uxguide/ctrl-status-bars): строка
  состояния — правильное место для текущего пути и краткого контекстного статуса.

**Раскладка.** `CommandBar` сверху, ниже три колонки: `ListView`-рейка корзин, `TreeView` с папками
и файлами, панель предпросмотра. Границы колонок двигаются стандартным `Thumb` (в WinUI 3 нет
`GridSplitter`; проверено по `Microsoft.WinUI.dll`). Кнопки «Дерево» и «Просмотр» не нужны:
панели всегда видимы. «Открыть папку» и «Скопировать путь» вынесены на панель, в `…` остались
только настройки.

**Live-наблюдение.** Один `FileSystemWatcher` на активную корзину, `IncludeSubdirectories = true`,
только пока окно видимо. `NotifyFilter` — `FileName | DirectoryName | CreationTime | LastWrite |
Size`, без `LastAccess`. Буфер 64 КБ, debounce 500 мс: пачка событий даёт одно обновление дерева.
При переполнении/ошибке watcher пересоздаётся и дерево читается один раз. Свои операции
подавляют события watcher на 1 секунду, чтобы не делать второй refresh. При скрытии в трей
наблюдение выключается; `F5` и показ окна остаются резервными.

**Сортировка и перемещение.** Ручной порядок материалов удалён вместе с `materialOrder`, drag
reorder, `Alt+↑`/`Alt+↓` и пунктами меню. Сортировка — Explorer: сначала папки, затем файлы, по
имени с естественным порядком чисел (`NaturalStringComparer`: `file2` раньше `file10`).
Перетаскивание узла на папку перемещает его; `Ctrl+X`/`Ctrl+C`/`Ctrl+V` работают с файлами и
папками.

**Папки и копирование.** Создание, переименование и удаление папки (в Корзину Windows с
подтверждением) выполняются в Core. Копирование папки рекурсивное; junction/symlink пропускаются,
чтобы не зациклиться и не выйти за пределы корзины; коллизии получают ` (2)`. Корень корзины
нельзя переименовать, удалить или переместить.

**Состояние.** `state.json` версии 3 хранит `selectedFolder` каждой корзины и больше не пишет
`materialOrder`. Файл версии 2 читается: `materialOrder` десериализуется и игнорируется, папки и
файлы на диске не трогаются. Это проверено на копии реальных данных пользователя: 5 корзин,
8 файлов и 5 папок остались нетронутыми, активная корзина сохранилась.

**Дополнительные исправления UX, сделанные в этом же заходе.**

- Двойной щелчок по названию больше не переименовывает: двойной щелчок по файлу открывает,
  по папке — разворачивает; переименование — `F2` или контекстное меню.
- Краткие сообщения ушли из InfoBar в строку состояния; ошибки в InfoBar не исчезают сами.
- «Настройки» убраны в переполнение `CommandBar`; на панели видны «Вставить», «Новая папка»,
  «Обновить», «Открыть папку», «Скопировать путь».
- «Открыть папку» открывает текущую папку, а не корень корзины.
- `Ctrl+T`, `Ctrl+W`, `Ctrl+1…9` переключают корзины; `Ctrl+Shift+↑/↓` меняют их порядок.
- Путь и счётчик в строке состояния относятся к текущей папке, а не к корню корзины.

**Историческая проверка до объединения harness.** 301 юнит-тест; базовый smoke — 5/5; headless UIA-прогон (окно за экраном,
без активации и трея) — 15/15: рейка корзин, дерево, live-обновление при внешнем файле,
текстовый и графический предпросмотр, копирование пути, вставка текста и папки, создание папки,
сохранение выбранной папки; миграционный прогон на копии реальных данных — 7/7. Debug и Release
собираются. Скриншоты окна сняты через `PrintWindow` с off-screen окна, поэтому приложение не
мелькало на рабочем столе.

**Ограничения.** Множественный выбор не добавлен; live-наблюдение работает только для активной
корзины и только при видимом окне; HTML/PDF встроенно не рендерятся; очень большие текстовые файлы
читаются частично.
