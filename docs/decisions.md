# Принятые решения

Требования: [`docs/discovery/brief.txt`](discovery/brief.txt). Решения по открытым вопросам
приняты в порядке из skill `prior-art-first`: сначала требования и проверенные факты среды, затем
официальные рекомендации Microsoft, затем практика разработки Windows-приложений. Решения, которые
противоречат рекомендации Microsoft, приняты только потому, что этого требует бриф.

## 1. UI-платформа: WinUI 3 + Windows App SDK 2.5.1, .NET 9

**Почему.** Бриф требует «современное приложение для Windows на C#/.NET» и «нативные элементы
интерфейса», а спорные решения велел разрешать по рекомендациям Microsoft. Microsoft называет
WinUI 3 рекомендованным нативным UI-фреймворком для новых Windows-приложений:
[«WinUI 3 is the recommended native UI framework for building new Windows desktop applications»](https://learn.microsoft.com/en-us/windows/apps/winui/winui3/).
WPF при этом не устарел — [FAQ: «WPF is supported … It remains a good choice for existing WPF
apps and for new apps whose requirements fit WPF»](https://learn.microsoft.com/en-us/windows/apps/get-started/windows-developer-faq).
WinUI 3 выбран потому, что он даёт современные Fluent-контролы и `TabView`, которые ближе всего к
прототипу, и при этом позволяет использовать нативные Win32-элементы там, где это важно
(TaskDialog, трей, Корзина Windows).

**Проверено в среде, а не по памяти:** минимальный WinUI 3-проект собран и запущен на этой машине
(.NET 9 SDK 9.0.308, Windows App SDK 2.5.1, `WindowsAppSDKSelfContained=true`, распаковка без
MSIX). Windows App SDK не требует установки рантайма на машине пользователя — он поставляется
вместе с приложением.

**Альтернатива.** WPF на .NET 10 остаётся разумным fallback, если понадобится Windows 10 в
условиях, где WinUI 3 недоступен. Отказ от WinUI 3 сейчас потребовал бы либо NuGet-доступа к
Windows App SDK (в этой среде сеть была ограничена), либо отдельной установки рантайма — оба
варианта хуже для воспроизводимой сборки.

**Ограничение.** WinUI 3 требует Windows 10 1809+; проверено на Windows 11 (сборка 26200).

**Стандартные контролы, а не копия прототипа.** Первая итерация интерфейса повторяла визуальный
стиль прототипа (кастомный заголовок, кастомные стили кнопок и полей). Заказчик явно потребовал
стандартное Windows-приложение: стандартные элементы, системная тема и аккуратный дефолтный вид,
а прототип использовать только как источник состава и расположения элементов. Интерфейс переделан
на дефолтные Fluent-контролы и стандартный заголовок окна (см. раздел 10).

## 2. .NET 9, с запланированным переходом на .NET 10 LTS

SDK 9.0.308 — единственный установленный; WinUI 3 и Windows App SDK 2.5.1 собираются и
запускаются на нём (проверено). .NET 9 — Standard Term Support, [поддержка до
10.11.2026](https://dotnet.microsoft.com/platform/support/policy/dotnet-core). Код не использует
API, специфичных для .NET 9, поэтому миграция — смена `TargetFramework` на
`net10.0-windows10.0.19041.0` после установки SDK 10 (LTS до 14.11.2028). Зафиксировано в README
как известное ограничение.

## 3. Состояние вкладок: JSON в `%LOCALAPPDATA%\PasteHatch\state.json`

Бриф оставлял формат открытым. Выбран один JSON-файл:

- `version` — версия схемы;
- `activeUid` — активная вкладка;
- `tabs[]` — порядок, UID папки, отображаемое имя и порядок материалов (`materialOrder`);
- `window` — позиция/размер плавающего окна в физических пикселях.

Запись атомарная (`.tmp` + `File.Move(overwrite)`), чтение устойчиво к битому/отсутствующему файлу.
**Файлы на диске — источник истины:** папки в `Baskets` сканируются при старте, папки с валидным
UID, не попавшие в state, «усыновляются» (имя — по времени создания папки), а записи о
несуществующих папках отбрасываются. Поэтому потеря/порча `state.json` не теряет материалы.
Ограничение: если папок с валидным UID больше 10, восстанавливаются первые 10 — лишние папки
остаются на диске и не удаляются.

## 4. Вкладки: нативный `TabView`, максимум 10, последняя не закрывается

Microsoft для сценария «пользователь динамически открывает и закрывает вкладки» рекомендует
`TabView` ([tabs guidance](https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/tab-view)),
а также требует, чтобы «there should always be an active tab». Отсюда:

- `TabView` + встроенная кнопка `+` (`AddTabButton`), которая отключается на 10 вкладках;
- вкладка закрывается через встроенную кнопку `×` только после подтверждения;
- вкладка с одной корзиной не закрывается (инвариант «всегда есть активная вкладка», совпадает
  с поведением прототипа);
- двойной щелчок по вкладке включает встроенное переименование (`Enter` — сохранить,
  `Esc` — отменить);
- вкладки переставляются перетаскиванием, порядок сохраняется (см. §17).

## 5. Подтверждения: нативный TaskDialog, «Отмена» по умолчанию

- Бриф требует подтверждение перед отправкой в Корзину Windows.
- Microsoft UX guidance: подтверждение — модальный диалог, самый безопасный вариант должен быть
  кнопкой по умолчанию, разрушительное действие — нет
  ([Dialog Boxes](https://learn.microsoft.com/en-us/windows/win32/uxguide/win-dialog-box),
  [Confirmations](https://learn.microsoft.com/en-us/windows/win32/uxguide/mess-confirm)).
- Реализация — нативный Win32 TaskDialog (`System.Windows.Forms.TaskDialog`, который доступен в
  .NET через WinForms-профиль): кнопки «Отмена» (default) и «В Корзину Windows», иконка Warning;
  для корзины путь показывается в раскрывающемся блоке.

**Конфликт с рекомендацией Microsoft.** В [Confirmations](https://learn.microsoft.com/en-us/windows/win32/uxguide/mess-confirm)
фраза «moving a folder to the Recycle Bin» приведена как пример ненужного подтверждения, потому что
Корзина и есть undo. Приоритет отдан требованию брифа: подтверждение обязательно. Вместо
кастомного оверлея из прототипа используется нативный диалог (требование «нативные элементы»).

## 6. Трей: приложение живёт в области уведомлений

- Бриф: «при закрытии окна приложение остаётся в области уведомлений; правый щелчок по значку
  открывает меню с командой «Показать окно»».
- Реализация: WinForms `NotifyIcon` (обёртка над `Shell_NotifyIcon`). Левый щелчок по значку
  показывает/скрывает окно (привычное поведение утилит в трее); правый щелчок открывает меню
  **Показать окно** (bold, default), **Настройки**, разделитель, **Выход**; подсказка «PasteHatch».
- **Запуск.** Обычный запуск окно не показывает — приложение сразу живёт в трее; окно
  открывается щелчком по значку, командой «Показать окно», повторным запуском (single instance)
  или аргументом `--show`. Исключение — самый первый запуск (когда ещё нет `settings.json`): окно
  показывается один раз, чтобы пользователь нашёл приложение; это поведение отключается
  настройкой «Запускать в трее».
- **Окно действительно выходит на передний план.** WinUI 3 `Window.Activate()` не поднимает уже
  существующее окно, которое находится позади других, — это открытый дефект платформы
  ([microsoft/microsoft-ui-xaml#7595](https://github.com/microsoft/microsoft-ui-xaml/issues/7595)).
  Поэтому показ из трея после `Show()`/`Restore()` дополнительно вызывает Win32
  `SetForegroundWindow`; если Windows отказала в смене активного окна
  ([правила `SetForegroundWindow`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow)),
  окно всё равно поднимается в z-порядке без активации, чтобы пользователь его увидел. Тот же
  нативный вызов использует WinUIEx в обработчике левого щелчка по значку
  ([WindowManager.TrayIcon.cs](https://github.com/dotMorten/WinUIEx/blob/main/src/WinUIEx/WindowManager.TrayIcon.cs)).
- **Свёрнутое окно — не «видимое».** Win32 `IsWindowVisible` возвращает true и для свёрнутого
  окна, поэтому прежняя проверка «видимо → спрятать» по щелчку по значку прятала свёрнутое окно
  вместо восстановления. Теперь `IsIconic` отличает свёрнутое окно от видимого, и щелчок
  восстанавливает его на переднем плане.
- **Конфликт с рекомендацией Microsoft.** [Notification Area guidance](https://learn.microsoft.com/en-us/windows/win32/uxguide/winenv-notification)
  не рекомендует минимизацию в трей («Use the Minimize button … not the Close button») и советует
  меню «Open / Options / Exit». Требование брифа (жить в трее) приоритетнее; порядок меню и
  добавленная команда «Выход» следуют этой рекомендации.
- Один экземпляр приложения: именованный `Mutex` + событие; повторный запуск показывает окно
  работающего экземпляра и завершается. Это предотвращает два трей-значка и конфликт записи
  `state.json`.

## 7. Контекстное меню материала: нативный `MenuFlyout`

Microsoft: для элемента с основным назначением (текст/изображение) используется контекстное меню;
команды не должны быть доступны только из него; команда, требующая подтверждения, получает
многоточие; в меню не показывают сочетания клавиш
([Menus and context menus](https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/menus-and-context-menus),
[Command Menus](https://learn.microsoft.com/en-us/windows/win32/uxguide/cmd-menus)).

Реализовано: `Открыть`, `Переименовать`, `Скопировать путь`, разделитель, `Переместить вверх`,
`Переместить вниз`, разделитель, `Удалить…` (многоточие — дальше подтверждение); меню
открывается правым щелчком, `Shift+F10` и клавишей меню; те же действия доступны с клавиатуры
(`Enter`, `F2`, `Delete`, `Alt+↑`/`Alt+↓`) и кнопками в строке — ничего не спрятано только в меню.

## 8. Буфер обмена и форматы материалов

Порядок разбора содержимого буфера: **FileDrop → Bitmap → UnicodeText** ([Standard clipboard
formats](https://learn.microsoft.com/en-us/windows/win32/dataxchg/standard-clipboard-formats)).
Чтение повторяется 10 раз по 40 мс при занятом буфере — официально документировано только то, что
«only one window can have the clipboard open at a time»; политика повторов — распространённая
практика, не документированная рекомендация.

Сохранение:

| Тип | Формат | Имя |
| --- | --- | --- |
| Скриншот/изображение из буфера | `.png` | `Пн, 13-02.png` |
| Текст из буфера | `.txt`, UTF-8 без BOM | `Пн, 13-02.txt` |
| Ссылка (однострочный http/https URL) | `.url` (Internet Shortcut, нативный формат Windows) | `Пн, 13-02.url` |
| Файлы из буфера/перетаскиванием | копия без изменения содержимого | исходное имя |
| Быстрая заметка | `.txt`, UTF-8 без BOM | `Пн, 13-02.txt` |

**Двоеточие и NTFS.** Бриф приводит имя заметки `Пн, 13:02.txt`, однако на Windows `:` в имени
файла запрещён: для NTFS это разделитель альтернативного потока данных (ADS), поэтому
`File.WriteAllText("Пн, 13:02.txt")` создаёт файл `Пн, 13` с потоком `02.txt`, а не ожидаемый файл
(дефект был найден юнит-тестами и исправлен). Поэтому имя вкладки/отображаемое имя остаются
`Пн, 13:02` (как в брифе), а имя файла формируется функцией
`TabNameFormatter.FormatAsFileName` — все недопустимые для файловой системы символы заменяются
на `-`: `Пн, 13-02.txt`. Это зафиксировано тестами.

Коллизии имён разрешаются суффиксом ` (2)`, ` (3)` — соглашение Проводника Windows. Расширение
при переименовании не меняется; недопустимые символы, служебные имена (`CON`, `NUL`, `COM1`…),
точка/пробел в конце и превышение длины отклоняются с нативным сообщением об ошибке.

## 9. Именование корзин и UID

- Имя по умолчанию — сокращённый день недели и время: `Пн, 13:02` (пример из брифа). Культура
  зафиксирована `ru-RU`, потому что интерфейс русский и имя не должно зависеть от языка ОС.
- UID папки — 6 символов из алфавита без похожих `I/O/0/1` (как в прототипе), уникален среди
  папок и открытых вкладок.
- Отображаемое имя вкладки хранится в `state.json` и не является именем папки — переименование
  вкладки не ломает путь, который пользователь передал агенту.

## 10. Визуальный язык: стандартные WinUI-контролы и системная тема

**Почему.** Пользователь попросил «выглядеть как дефолтное Windows-приложение, красивое и
аккуратное», а прототип оставить только как источник состава экрана. Это совпадает с официальными
принципами Windows 11 — [«Calm: Windows 11 is softer and decluttered» и «Familiar: … There is no
learning curve»](https://learn.microsoft.com/en-us/windows/apps/design/design-principles) — и с
руководством по настройкам: «Keep settings pages simple and make use of binary (on/off) controls.
A toggle switch is usually the best control for a binary setting», «Define smart defaults and keep
the number of settings to a minimum», «When a user changes a setting, the app should immediately
reflect the change» ([Guidelines for app settings](https://learn.microsoft.com/en-us/windows/apps/design/app-settings/guidelines-for-app-settings)).

Что из этого следует и реализовано:

- **Стандартный заголовок окна** с системными кнопками «свернуть/развернуть/закрыть»; кастомные
  заголовок и caption-кнопки удалены (заодно ушла проблема «лишней» кнопки maximize).
- **Только дефолтные контролы и стили Fluent**: `TabView` для корзин, `CommandBar` для команд,
  `ListView` для материалов, `TextBox` + `Button` для быстрой заметки, `InfoBar` для статуса,
  `MenuFlyout` для контекстного меню, `ToggleSwitch` в настройках. Кастомный словарь стилей из
  `App.xaml` удалён.
- **Системная тема**: приложение следует светлой/тёмной теме Windows; для тёмной темы title bar
  синхронизируется через `DWMWA_USE_IMMERSIVE_DARK_MODE` (WinUI 3 не всегда применяет его для
  unpackaged-приложений).
- **Структура экрана**: вкладки → панель команд → список материалов → быстрая заметка → InfoBar →
  строка состояния с путём корзины и числом файлов. Это соответствует командному паттерну
  ([Command bar](https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/command-bar):
  «Command bars provide users with easy access to your app's most common tasks») и убирает визуальный
  шум прототипа.
- **Настройки — отдельное окно** с тремя булевыми настройками (запуск в трее, запоминание
  положения окна, поверх других окон), сразу применяются без OK/Cancel; точка входа — последняя
  команда на панели и пункт в меню трея, как рекомендует руководство по настройкам.
- **Компактность**: окно по умолчанию 820×680 DIP вместо 1000×860, при этом свободно
  растягивается; первый запуск открывает окно, дальше приложение живёт в трее.
- **Создание корзины — только кнопкой `+` в строке вкладок.** Отдельная команда «Новая корзина»
  на панели команд удалена: она дублировала вкладки и не добавляла ничего сверх встроенной
  кнопки `+` в `TabView` (замечание заказчика).

## 11. Остальные решения

- **Первый запуск** создаёт одну пустую корзину и один раз показывает окно; дальше приложение
  стартует в трее (см. раздел 6).
- **Папки в drag&drop/буфере** отклоняются с сообщением: бриф говорит про файлы; избегаем
  неявного копирования произвольных деревьев.
- **Живого `FileSystemWatcher` нет**: список обновляется при переключении вкладок, добавлении
  материалов и показе окна из трея. Требования не просят live-sync.
- **Иконка приложения** генерируется скриптом `scripts/generate-icon.ps1` (многоразмерный `.ico`,
  32-битные DIB-записи для совместимости с Win32/WinUI), бинарник не редактируется вручную.
- **Настройки** хранятся отдельно от состояния вкладок — в `settings.json`, чтобы повреждённый
  файл настроек не влиял на корзины. Те же три значения имеют разумные дефолты и сбрасываются
  командой «Сбросить настройки» в окне настроек.
- **Тестовые швы** (в обычной работе не задаются): `PASTEHATCH_DATA_ROOT` изолирует папку данных,
  `PASTEHATCH_TEST_OFFSCREEN=1` показывает окно за пределами экрана без активации,
  `PASTEHATCH_TEST_NO_TRAY=1` не создаёт значок в трее. Всё это нужно, чтобы автоматические
  проверки не появлялись на рабочем столе пользователя. По умолчанию путь всегда
  `%LOCALAPPDATA%\PasteHatch` через
  [`Environment.SpecialFolder.LocalApplicationData`](https://learn.microsoft.com/dotnet/api/system.environment.specialfolder),
  как требует бриф.

## 12. Тестирование: юнит-тесты ядра + базовый smoke

- **Домен покрыт юнит-тестами** (`tests/PasteHatch.Core.Tests`, xUnit, 280 тестов): именование,
  классификация, состояние, восстановление, коллизии, подтверждения, лимит вкладок, ADS-регрессия,
  превью первых строк.
  Это дешёвые и стабильные проверки, которые стоит держать зелёными.
- **UI проверяется базовым smoke-тестом** (`scripts/smoke.ps1`, 5 проверок): запуск, создание
  корзины и state, окно, добавление текста через кнопку «Вставить», единственный экземпляр.
  Сложный UI-сценарий на 20 шагов (диалоги, клавиатурные комбинации, drag & drop, изолированный
  рабочий стол) был написан, прогнан и **удалён**: приложение будет активно дорабатываться, такие
  сценарии хрупкие и дорогие в поддержке, а их провалы чаще означают проблемы самой автоматизации.
  Поэтому спорные места проверяются одноразовыми ручными прогонами, а в репозитории остаётся
  только базовая проверка «приложение живо и делает минимум».
- **Осторожность к пользователю**: smoke-тест запускает окно за пределами экрана, без активации и
  без значка в трее, поэтому не мешает работе за компьютером.

## 13. Список материалов: без анимаций появления

**Дефект.** При переключении вкладок список на секунду становился пустым, хотя данные уже были
готовы. Измерено на машине разработки: UI Automation отдаёт строки новой вкладки через 2–8 мс после
выбора вкладки, а кадры экрана (запись области списка, ~100 мс на кадр) показывают пустой список
примерно с 120 мс до 1000 мс после переключения — новые строки проявлялись только к 1–1.2 с.

**Причина.** Стандартный шаблон `ListView` задаёт `ItemContainerTransitions` — переходные анимации
добавления, удаления и перестановки элементов; свойство и способ его переопределить документированы
Microsoft
([ItemsControl.ItemContainerTransitions](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.xaml.controls.itemscontrol.itemcontainertransitions)).
`SyncMaterialRows` удаляет строки старой вкладки и вставляет строки новой, поэтому анимация
удаления/добавления срабатывала на каждый переход. Это была именно анимация, а не ленивая
подгрузка и не проверка безопасности: строки в UI Automation появлялись сразу.

**Решение.** Для `MaterialsList` в `MainWindow.xaml` задан пустой `ItemContainerTransitions` —
содержимое показывается в том же кадре. Проверено повторной записью кадров: после правки первый же
снятый кадр содержит строки новой вкладки, пустого кадра и секундной задержки нет.

## 14. Превью первых строк для текстовых и Markdown материалов

**Требование заказчика.** Для `.txt` и `.md` файлов в списке видно несколько первых строк, чтобы
файл с именем по времени (`Пн, 13-02.txt`) можно было узнать, не открывая.

**Решение.** `MaterialPreview.Read` в Core читает ограниченный фрагмент (первые 2048 символов,
UTF-8 с определением BOM, `FileShare.ReadWrite | FileShare.Delete`, чтобы файл, открытый в другой
программе, всё равно превьюился), берёт первые две непустые строки, обрезает результат до 200
символов и завершает обрезку многоточием. Любая ошибка чтения (нет файла, нет прав, пустой файл)
даёт `null`, и строка показывает прежнюю подпись типа. Ограничение фрагмента — не оптимизация
ради оптимизации: в корзине может лежать большой файл, и список не должен читать его целиком.

**Визуально** подпись превью заменяет общую подпись «Текст» только у текстовых/Markdown файлов;
изображения, ссылки и прочие материалы продолжают показывать тип. `MaterialRow` читает превью при
создании строки — перерисовка списка и его модель данных не меняются.

## 15. Копирование пути конкретного файла

**Требование заказчика.** В списке материалов нужна такая же кнопка копирования пути, как у
папки корзины, но для отдельного файла: путь к конкретному материалу передаётся агенту.

**Решения и почему.**

- **Кнопка в строке, справа.** [Buttons](https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/buttons):
  «If your button appears within a container UI (for example, within a toast notification, a
  flyout, or a list view item), you should right-align the button within the container.» Чтобы
  кнопка действительно встала у правого края, строка растянута на всю ширину:
  `HorizontalContentAlignment="Stretch"` в `ItemContainerStyle` — приём, показанный в
  [Item containers and templates](https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/item-containers-templates).
  Без этого `ListViewItem` выравнивает содержимое влево, и кнопка оказалась бы сразу после текста.
- **Кнопка видна всегда.** В [Contextual commanding](https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/collection-commanding)
  кнопки у элемента списка — это mouse/pen accelerator, и их можно показывать только при
  наведении. Здесь выбран постоянный показ: копирование пути — основной сценарий продукта, а
  постоянная кнопка доступна мышью, тачем и клавиатурой без дополнительных жестов.
- **Команда есть и в контекстном меню.** Там же: «you should make all commands for an item
  available in the item's context menu» и «At a minimum, use a context menu to provide access to
  all commands». Пункт «Скопировать путь» добавлен между «Переименовать» и «Удалить…», поэтому
  клавиатура и тач получают команду через контекстное меню.
- **Иконка без подписи, но с именем.** [Accessibility overview](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/accessibility-overview):
  важнейшая информация для screen reader — accessible name. У кнопки заданы
  `AutomationProperties.Name` и tooltip «Скопировать путь к файлу».
- **Путь без кавычек.** Как и путь папки, строка копируется простым текстом: её получатель —
  локальный агент, а не командная строка. Формат совпадает с существующей кнопкой
  «Скопировать путь».
- **Буфер — тот же сервис.** `BasketWorkspace.CopyMaterialPath` вызывает
  `IShellService.CopyText` (повторы при занятом буфере уже реализованы в `ShellService`), ставит
  статус «Путь к файлу скопирован в буфер обмена.» и сообщает об ошибке так же, как копирование
  пути папки.

**Проверено.** Юнит-тесты: копируется путь именно выбранного материала, ошибка буфера
показывается пользователю, изменение приходит одним событием `Changed`. Одноразовый UIA-прогон
(окно за экраном, без трея): кнопка находится по имени, клик кладёт в буфер полный путь файла
(а не папки), кнопка стоит у правого края строки (зазор ≈12 DIP), кнопка копирования пути папки
продолжает работать. Снимок окна с тремя материалами подтвердил вид строк.

## 16. Переименование с видимым расширением и порядок материалов

**Требования заказчика.** Переименование — кнопкой в строке и/или двойным щелчком по названию,
при этом редактируется только имя, а расширение видно рядом и не меняется. Материалы меняют
порядок перетаскиванием; порядок сохраняется.

**Почему так.**

- **Явная кнопка — основная точка входа.** [Mouse and pointers](https://learn.microsoft.com/en-us/windows/win32/uxguide/inter-mouse):
  двойной щелчок выполняет default command, «advanced interactions must have consistent,
  predictable behavior», а «Don't make double-clicking and dragging the only way to perform an
  action». Поэтому переименование доступно кнопкой в строке, `F2` и пунктом контекстного меню;
  двойной щелчок по названию — дополнительный ускоритель по просьбе заказчика, а двойной щелчок
  по остальной строке сохраняет default command — открыть материал.
- **Расширение видно и не редактируется.** Инлайн-редактор содержит только базовое имя;
  расширение — отдельная подпись рядом, коммит сохраняет расширение. Это требование заказчика и
  привычное поведение Проводника; в Core расширение уже не менялось (`RenameMaterial`).
- **Порядок — метаданные, файлы — источник истины.** [ListViewBase.CanReorderItems](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/api/winrt/microsoft.ui.xaml.controls.listviewbase.canreorderitems):
  для встроенного reorder нужны `CanReorderItems` и `AllowDrop`, а `CanDragItems` — чтобы приходили
  события. Отдельно требуется [ReorderMode](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/api/winrt/microsoft.ui.xaml.controls.listviewbase.reordermode):
  по документации значение по умолчанию — `Disabled`, и без `Enabled` перетаскивание не меняет
  порядок (проверено на этой сборке: с `Disabled` drop отменялся). Перетаскивание меняет
  привязанный `ObservableCollection` (Remove+Insert), поэтому порядок сохраняется в `state.json`
  (`tabs[].materialOrder`) при завершении drag. Имена, которых больше нет, игнорируются, новые
  файлы добавляются в конец; переименование сохраняет слот, удаление убирает запись. Так порядок
  переживает перезапуск и внешние изменения папки.
- **Клавиатурная альтернатива.** [Keyboard accessibility](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/keyboard-accessibility)
  требует, чтобы действия были доступны с клавиатуры; по [Mouse and pointers](https://learn.microsoft.com/en-us/windows/win32/uxguide/inter-mouse)
  нельзя делать dragging единственным способом действия. Поэтому добавлены `Alt+↑`/`Alt+↓` и
  пункты «Переместить вверх/вниз» в контекстном меню.
- **Внешний drag&drop не сломан.** ListView с `AllowDrop` получает и внешние файлы; его обработчики
  `DragOver`/`Drop` пробрасывают их в те же методы окна, а внутренний reorder распознаётся по
  `DragItemsStarting`, чтобы два вида drag не конфликтовали. Окно при этом не должно сбрасывать
  `AcceptedOperation` во время внутреннего drag — иначе встроенный drop отменяется.

**Проверено.** 280 юнит-тестов, из них 9 новых на порядок (сохранение/восстановление, Move,
rename сохраняет слот, delete убирает запись, внешние и пропавшие файлы). UIA-прогон: кнопка
переименования открывает редактор с именем без расширения и отдельной подписью расширения,
сохранение переименовывает файл на диске и оставляет расширение. Отдельные одноразовые прогоны с
синтезированным вводом: двойной щелчок по названию открывает редактор (по остальной строке
сохраняется открытие файла), а drag первого материала в конец списка даёт порядок
`b.txt, c.txt, a.txt` и тот же порядок в `state.json` (drop принят как Move).

## 17. Перестановка вкладок-корзин

**Требование заказчика.** Вкладки (корзины) можно переставлять друг относительно друга
перетаскиванием; порядок сохраняется.

**Почему так.**

- **Встроенный reorder TabView.** Для документа-подобных вкладок Microsoft называет
  перестановку одним из основных сценариев ([Tab view](https://learn.microsoft.com/en-us/windows/apps/design/controls/tab-view)).
  [CanReorderTabs](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/api/winrt/microsoft.ui.xaml.controls.tabview.canreordertabs)
  по умолчанию `true`, но в §4 был выставлен `false`, поэтому перестановки не было; включили
  `CanReorderTabs="True"`. `CanDragTabs` оставили `false`: он про drag вкладки как data payload
  между окнами ([CanDragTabs](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/api/winrt/microsoft.ui.xaml.controls.tabview.candragtabs)),
  для перестановки внутри одного TabView не нужен.
- **Синхронизация порядка.** Встроенный reorder меняет `TabItems`, а не модель workspace. Порядок
  считывается в [TabItemsChanged](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/api/winrt/microsoft.ui.xaml.controls.tabview.tabitemschanged)
  и откладывается через `DispatcherQueue`: перестановка приходит как Remove+Insert (два изменения),
  а синхронизация пропускается, пока полоса вкладок перестраивается из workspace (`_isUpdatingUi`),
  иначе получился бы цикл «UI → модель → UI».
- **Хранение.** Порядок вкладок уже является частью `state.json` (`tabs[]`), поэтому схема не
  менялась: `ReorderTabs`/`MoveTab` переставляют `_tabs` и сохраняют состояние. Неизвестные UID
  игнорируются, отсутствующие вкладки добавляются в конец — устаревший drag не может потерять
  открытую корзину.
- **Клавиатурная альтернатива.** [Keyboard accessibility](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/keyboard-accessibility)
  и [Mouse and pointers](https://learn.microsoft.com/en-us/windows/win32/uxguide/inter-mouse)
  («Don't make double-clicking and dragging the only way to perform an action») требуют не
  оставлять перестановку только мышью. Добавлены `Ctrl+Shift+←`/`Ctrl+Shift+→`; обработчик —
  `PreviewKeyDown` на TabView, чтобы стрелка не была перехвачена встроенной навигацией по вкладкам.
  Во время переименования вкладки сочетание остаётся текстовому полю.

**Проверено.** 6 новых юнит-тестов: порядок переживает перезапуск, неизвестные и пропавшие UID,
`MoveTab`, активная вкладка не меняется, границы списка. Одноразовый прогон с синтезированным
вводом: drag третьей вкладки на первое место дал порядок `CCCCCC, AAAAAA, BBBBBB` в `state.json`,
активная вкладка осталась `AAAAAA`; `Ctrl+Shift+→` переставил активную вкладку вправо —
`CCCCCC, BBBBBB, AAAAAA`.
